# Customer integrations and background work

Pluto uses a separate commercial bot token and webhook secret. Customer Settings issues 10-minute, one-time, 192-bit pairing codes; only their SHA-256 hashes are stored. The secret-authenticated webhook validates private, nonforwarded messages and routes Telegram IDs through a restricted worker function. Bot/person and bot/chat identities are unique. Pairing cannot take over another customer's chat. Disconnect removes routing and cancels pending replies. Never configure the personal bot here.

Existing money quick entry, exact balance arithmetic, undo, tasks, notes, reminders and local `/ask` analysis remain. Free allows 20 commands/day, Plus 500 and Pro 2,000, configured in PlanCatalog. A database trigger atomically checks the current entitlement and daily count; transaction rollback prevents partial writes on rejection. Updates replay without duplicate records. Reply outbox leases, attempt limits and fencing prevent stale completion. Telegram delivery cannot be guaranteed exactly once after an uncertain network outcome; messages may repeat in that case. No private provider keys are sent to chats.

Existing read-only Google/Apple Calendar, Canvas and GitHub adapters keep encrypted customer-scoped grants and bounded retries. Gmail/Drive remain hidden. Automatic banking remains retired. New authorizations/discovery require the server-side integration flag; disconnect remains available. Free/Plus/Pro allow 1/3/10 live connectors. Quotas are database-enforced. Connector encryption binds customer, connection and provider as authenticated context; a separate commercial encryption key is mandatory. Provider registration/consent and real connector acceptance are still owner tasks.

Hosted work is opt-in with PLUTO_WORKERS_ENABLED. The restricted pluto_worker_runtime login inherits customer RLS and calls narrow claim/routing functions; request handling uses a different login. A bounded fair dispatcher claims at most two customers, with five-minute leases, fencing and backoff. Each task opens an explicitly scoped transaction and verifies active customer status. Customer notifications retain existing durable job keys, per-job leases, retries and in-app history. Canvas feed refresh retains consent, refresh intervals and adapter leases. Dormant/Free accounts never enqueue paid weekly reports. Report reads never enqueue jobs. Optional report-ready Telegram messages use a persisted outbox and contain no report content.

Hourly canonical Stripe reconciliation is separately flagged and uses billing credentials only. Auth deletion is separately flagged and uses pluto_erasure_runtime plus a commercial Auth admin key. That role can claim only a self-requested deleted customer's ticket and complete the matching fenced deletion; it cannot read customer records. Failed Auth removals lease/retry at most five times and require operator follow-up after exhaustion. The admin key is not used for normal customer authorization. All provider functions were tested with synthetic records/mocks, not live personal infrastructure.

An always-on process is required for scheduled reliability. A sleeping free host is insufficient. Multiple instances share database leases. Review worker failures and exhausted jobs before beta; external APIs still require live acceptance. Keep paid flags disabled during initial deployment and verify the dispatcher against synthetic commercial accounts first.

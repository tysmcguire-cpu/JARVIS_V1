# Pluto database and isolation

Never use personal database credentials. Create a separate commercial Supabase project, obtain its project reference, and review every migration before execution. Historical migrations are immutable; 20261022000000_pluto_foundation is additive and aborts if User contains any records. This intentionally prevents commercial conversion of an existing personal database. No commercial migration has been applied remotely.

The migration creates NOLOGIN pluto_app and grants runtime access under existing FORCE RLS ownership policies. Commercial identity/settings insertion policies allow only auth.uid(); status changes and administrative privileges are not granted. Browser anon/authenticated table access remains revoked. A separate restricted LOGIN role pluto_runtime must be provisioned as a member of pluto_app (not table owner, superuser or BYPASSRLS); use its pooler login for DATABASE_URL. Keep DIRECT_URL only in approved migration tooling. Never run a browser request with the admin URL.

PLUTO_SUPABASE_PROJECT_REF must match both Auth URL and database host/pooler username. Runtime URLs must use TLS and the pluto_runtime login; administrative URLs are accepted only by guarded migration tooling. The db:migrate wrapper additionally requires PLUTO_ALLOW_MIGRATIONS=approved. Old single-owner setup/restore/provision commands are deliberately retired and fail without connecting.

The installation metadata table is reserved for separately approved infrastructure provisioning. Further commercial schema changes and lifecycle procedures are tracked in PLUTO_ROADMAP.md. Local migration tests emulate Supabase prerequisites in PGlite and verify two real PostgreSQL roles/identities, ownership FKs and cross-tenant rejection. They do not replace live Supabase acceptance.

Lifecycle migration 20261022010000_pluto_lifecycle adds an inactive-customer restrictive RLS policy, locked erasure and a minimal authentication-removal queue. The definer function has no customer-ID parameter and is executable only by the runtime role; it derives auth.uid() and accepts only an active self account. Child deletion uses a fixed allowlist, not caller SQL. A customer tombstone remains until Auth removal. Customer transactions lock the profile FOR SHARE; erasure locks it FOR UPDATE to serialize in-flight records. A narrow self-update policy permits locking inactive profiles but its WITH CHECK blocks mutation/reactivation. No worker has erased a real Auth account.

Billing migration 20261022020000_pluto_billing defines catalog, global budget policy, customer mapping, canonical subscription cache, single checkout intents, minimal Stripe event/ledger/movement records and usage reservations. Customer role has SELECT-only own billing/usage access. Separate NOLOGIN pluto_billing role needs its own restricted login, and cannot read private tracking. Provider reservations/settlement are fixed definer functions scoped by auth.uid(), not arbitrary SQL. Global spend budget remains disabled/zero. Nullable user links anonymize retained business/usage aggregates when Auth deletion finally cascades the customer. Checkout/deletion guards require an active locked profile, fresh Stripe state, no open checkout and no active paid request.

## Final hardening
Installation identity is now checked for every configured runtime role and initialized only by approved migration tooling. Constant-space request counters enforce minute/day budgets. Fixed triggers account for rows and logical JSON bytes across tracking, imported records, conversations, reports and voice transcripts. Upserts, shrinking updates, deletion and tenant separation are tested. Global logical storage defaults to 128MiB; physical storage and retained billing/usage tables require operator monitoring. Restricted application roles cannot edit counters. Maintenance is fixed, leased and worker-only.

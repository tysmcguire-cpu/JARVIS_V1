# Pluto business administration

Administration is independent of customer authorization. `/admin` verifies a fresh, email-confirmed Auth identity, explicit active `owner_admin` membership, a currently enrolled factor, matching token subject and AAL2 on every read. The admin database login can execute only fixed membership/aggregate functions; it cannot select customer tables. Admin identities cannot become customer workspaces. No first-signup, email-match or browser-secret rule grants access. [Supabase MFA](https://supabase.com/docs/guides/auth/auth-mfa) provides enrollment and verification; there is no custom bypass.

Owner setup, only in the separate commercial project: create a separate Auth account, verify its email, sign in and enroll at `/mfa?next=admin`. Use `PLUTO_ALLOW_ADMIN_PROVISIONING=approved`, `PLUTO_ADMIN_AUTH_ID` and migration-only DIRECT_URL with `pnpm exec tsx scripts/pluto-admin.ts grant`. The script requires verified email, a verified MFA factor and no customer profile. It is not executed by app startup or this development task. Sign in through `/login?next=admin`. The `revoke` command disables membership immediately. Provisioning/read operations are audited without private record contents.

Configure restricted `pluto_admin_runtime` (member of pluto_admin) through PLUTO_ADMIN_DATABASE_URL and independent `pluto_admin_api_runtime` (member of pluto_admin_api) through PLUTO_ADMIN_API_DATABASE_URL. Neither role inherits pluto_app or billing privileges. Request credentials and worker credentials remain separate.

## Read-only API for the separate personal JARVIS

`GET /api/admin/metrics?from=YYYY-MM-DD&to=YYYY-MM-DD` accepts an Authorization bearer credential with only `metrics:read`. Date windows are at most 90 days within two years. There is no customer-record endpoint or arbitrary SQL parameter. Use `scripts/pluto-admin.ts issue-key` after explicit provisioning approval, with PLUTO_ADMIN_KEY_OUTPUT pointing to a private file **outside the repository**. It writes a random 256-bit credential once, stores only SHA-256, expires after 30 days and prints no credential. Protect the file using host file permissions; a failed DB commit may leave an inert file that must be removed manually before retrying.

Use `revoke-key` with PLUTO_ADMIN_API_KEY_ID and matching admin UUID to revoke a key, or `revoke` to disable all keys through membership. Valid keys receive a durable 30-requests/minute limit. Expired/revoked/unknown keys return 401; exhausted allowance returns 429. Responses are no-store. Successful reads record administrator/key/channel/time, not customer data. Invalid random credentials are not retained as unbounded audit rows.

Future **separately approved** personal-JARVIS change: store this new credential server-side in that application's own secret configuration; fetch this fixed endpoint over HTTPS with a 10-second timeout; validate the documented JSON DTO and display aggregate results with asOf/mode. Cache only aggregates briefly; never send the credential or response payload to Telegram. Rotate by issuing a new key, changing the personal secret, verifying one read, then revoking the old key. Do not use commercial database URLs, Supabase service keys, customer credentials or unrestricted AI SQL. **No personal-JARVIS source or deployment was changed.**

## Definitions and limitations

Registered counts begin at workspace profile creation, excluding unfinished Auth-only registrations. Aggregate registration/cohort records survive deletion with the customer ID removed; detailed per-customer activity is erased. Activation means completed onboarding. Ever-converted counts the first active canonical Stripe subscription and separates test/live billing. DAU/WAU/MAU are unique customers with minimal first-party feature counters in UTC through the selected end date. Cohort return rate is last-30-day activity by registration month, not a lifetime-retention prediction. Cancellation intent, churn events and trial state are distinct. No trial is enabled by default.

MRR/ARR are current active, unexpired, freshly reconciled Stripe subscription snapshots, with annual payments normalized monthly. Stale snapshots are disclosed and excluded. Cash collected, cumulative negative refunds, failed payments and observed revenue movements come from the canonical webhook/reconciliation pipeline. Historical date filters apply to events/usage; current MRR remains a current snapshot. Usage cost includes successful measurements and worst-case reserved cost for uncertain calls. Kind/model/tier breakdowns contain no customer identifiers or contents. Model/voice/research costs are estimates until verified against provider invoices.

OperatingCost values are owner-configured monthly USD microdollar estimates, initially NULL. Selected-period allocation uses days/30. Cash less refunds and estimated provider cost excludes processing fees, taxes, labor and other unconfigured expenses. Estimated operating surplus remains unavailable until all fixed-cost fields are configured and is never labelled actual net profit. Tier MRR and range usage columns do not establish tier profit. Real payment fees/invoices and business accounting still require reconciliation outside this initial dashboard.

The dashboard includes date filters, daily charts, comparison halves, subscriber/revenue/usage breakdowns, cohort tables, engagement and failed/stale worker/report/notification/deletion counts. No third-party analytics service is added. Live administrator MFA/browser flow and real API-key rotation need acceptance against the separate project. Independent security review remains mandatory before broad launch.

## Metric limits
Refund movement uses individual successful refund dates, not cumulative charge amounts placed in the newest period. Failed-payment count represents unique failed invoices, not every processor attempt. MRR is current fresh subscription state; selected-period revenue/costs are movements. Operating cost fields begin NULL. Aggregates are management estimates, not statutory accounting, and omit unconfigured processor/tax/operating costs. Global service failures require platform-log monitoring in addition to per-customer job metrics.
